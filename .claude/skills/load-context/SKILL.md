# Load Project Context

You are starting a task in a np-initialized project. Before doing anything else, load the project's ground truth so your work matches how this project actually builds software. Everything you need was generated by `/np-init` — never substitute memorized assumptions about the stack or layout.

## Procedure

### Step 1: Locate the profile (fail-closed)

Walk up from the current working directory to the nearest `.claude/np.config.json`.

**If it does not exist**: this project is not initialized. Stop and tell the user:

> np not initialized — run /np-init

Do not attempt to reconstruct project context by other means.

### Step 2: Load the project frame (cached per run)

The **frame** is the part of project context that is identical for every stage of
a run — the profile, the hard constraints, the module index. Plan, implement and
test all need it and all get the same bytes, so a run reads the source files
**once** and every later stage reads the distilled cache instead.

#### 2a. Is there a usable frame cache?

You have a cache to use only when your invocation names a `handoff_dir` (or you
can see `00-request.json` in one — pipeline stages always can). A dev invoking
this skill standalone has no handoff dir: skip to 2b and do not write a cache.

With a handoff dir, check `np_get_handoff(handoff_dir, "00-context.json")`:

- **Missing** → 2b (build it).
- **Present** → verify it is still current. Recompute the source hashes:

  ```bash
  shasum -a 256 .claude/np.config.json .claude/project_context/architecture.md .claude/project_context/modules.json
  ```

  Compare against the cache's `source_hashes`. **All three match** → use the
  cached frame as-is, skip 2b entirely, and go to Step 3. **Any mismatch** →
  a file changed during the run (a `/np-feedback` amendment, a dev edit);
  rebuild via 2b and overwrite the cache.

  Do NOT validate against `_meta.json` → `generated_hashes`. Those are the
  **init-time** hashes and are stale by design — these files are hash-guarded
  precisely so devs can edit them freely, so a mismatch there means "edited
  since init", not "changed during this run".

#### 2b. Build the frame from source

Read with the `Read` tool:

1. `.claude/np.config.json` — capture:
   - `project_name`
   - `stacks[]` — kind, roots, build/test/typecheck commands, `error_format`, `results_format`
   - `layout_families` — the families and their reference modules
   - `harness` — `runs_root` (run state only — code changes always happen in the working tree), `handoff_dirname`
2. `.claude/project_context/architecture.md` — read it and hold on to the **hard constraints** (mandated base classes, messaging/DI/wiring patterns, layering rules). These override any conflicting pattern found in code search results.
3. `.claude/project_context/modules.json` — skim the `modules[]` list so you know which module names exist and which family each belongs to. Read the entry for your target module in full (capabilities, `build_target`, `placement_notes`).

When you have a handoff dir, write what you distilled — **not the raw files** —
so the next stage reads a short digest instead of a long document:

```
np_write_handoff(handoff_dir, "00-context.json", {
  "schema_version": 1,
  "source_hashes": {"np.config.json": "<hex>", "architecture.md": "<hex>", "modules.json": "<hex>"},
  "project_name": "...",
  "stacks": [ /* kind, roots, commands, error_format, results_format */ ],
  "layout_families": { /* family id → reference module */ },
  "harness": {"runs_root": "...", "handoff_dirname": "..."},
  "hard_constraints": ["<one line per rule in architecture.md — the rule, not its examples>"],
  "modules_index": [{"name": "...", "family": "...", "capabilities": {}, "build_target": "...", "placement_notes": "..."}]
})
```

`hard_constraints` is the whole point of the cache: `architecture.md` carries
each rule with its Correct/Wrong pair, and only the rule survives into the
frame. Later stages that need a rule's example can still open the file.

Do NOT read `conventions.md` here — that is the `conventions` skill's job, invoked right before writing source files.

### Step 3: Load relevant lessons — ALWAYS fresh, never cached

Find active lessons and error-solutions that relate to the task at hand.

**This step runs every time, cache or no cache.** The frame is stage-independent;
lessons are not. Planning wants lessons about the target module, implementation
wants the ones about the patterns it is writing, and testing wants
error-solutions for the stack it is about to run. Caching this would quietly
hand every stage the *planning* stage's search results — the queries are cheap
and the relevance is the whole value, so they get re-run. New entries the
updater wrote earlier in the same session are picked up here too.

> **Resolving the code-search tool (do this before your first search).** The
> `search` tool is served by the **`np-code-search` MCP server**. Every host
> renames MCP tools with its own prefix, so do NOT assume a literal name — in
> Claude Code it appears as `mcp__plugin_np_np-code-search__search`; other
> hosts use a different prefix. Its schema may also be **deferred**, i.e. not
> loaded into your context yet, and the server may still be connecting at the
> start of a session. Resolve it in this order:
>   1. look for any available tool whose name ends in `search` and whose server
>      is `np-code-search`, and call it;
>   2. if your host has a deferred-tool loader (Claude Code: `ToolSearch`), call
>      it with the keywords `np-code-search search` — it also waits out a
>      server that is still connecting — then call the tool;
>   3. last resort, run the CLI twin, which ships with every install:
>      `bash .claude/bin/ccc-wrapper.sh grep "<query>"`.
>
> **Never silently fall back to Read/Grep because the tool "isn't there":**
> file reads miss the whole index. If it is genuinely unavailable after all
> three, say so explicitly in your output and note that results are degraded —
> do not pretend the index was consulted.

**Primary path — code index** (`np-code-search` MCP `search` tool):

```
search(query="<3-8 keywords describing the task>", paths=[".claude/project_context/lessons/**"], limit=5)
```

Run 1-3 searches with different keyword angles (feature nouns, module name, artifact kinds involved).

**Fallback — direct file read** (when the search tool is unavailable or errors):

- `context_list(kind="lesson", status="active")` and `context_list(kind="error-solution", status="active")` via the `np-workspace` MCP server, filtering by the target module; or
- List `.claude/project_context/lessons/` with the `Glob`/`Read` tools and read the frontmatter of entries whose `tags`/`modules` match the task. Skip anything with `status: superseded` and everything under `lessons/_archive/`.

Ignore superseded entries — their bodies are truncated pointers to their replacements.

### Step 4: (Optional) Business context

If the task involves domain behavior (not pure plumbing), also run:

```
search(query="<domain terms>", paths=[".claude/project_context/business/**"], limit=5)
```

or read `.claude/project_context/business/_index.md` and the relevant `<domain>.md` file.

### Step 5: Summarize what you loaded

Produce a compact working summary (for yourself and, when invoked by a dev, in your reply):

- Project + stacks (one line each)
- Target module → family, capabilities, build target
- The 3-5 hard constraints from `architecture.md` most relevant to this task
- Each relevant lesson/error-solution: id, one-line claim
- Any relevant business entries: anchor id, one-line summary

Carry this summary through the rest of the task. When something you discover contradicts it, prefer the observed code — and record the contradiction as a `context_findings` item (kind `correction`) if you are running inside a pipeline handoff.

## Rules

- Fail closed: no `np.config.json` → stop with "run /np-init".
- Search first, file-read fallback second — never skip lessons because search is down.
- Never load `lessons/_archive/` content.
- Keep the summary short; this skill loads context, it does not produce deliverables.
- **Frame cached, lessons fresh.** Re-reading `architecture.md` in every stage is
  the same bytes three times; re-running the lesson search is three different
  questions. Never cache Step 3, and never skip Step 2's hash check to save the
  one `shasum` call — a stale frame silently plans against constraints the dev
  has already changed.
- Only write `00-context.json` when you have a handoff dir. Standalone
  invocations read the sources directly and leave no cache behind.
